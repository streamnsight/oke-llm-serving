# Project status

Discovery inputs cover the model/workload, capacity scope and report/bundle publication. Optional monitoring, autoscaling and weight delivery are configured downstream; recommendations do not freeze the model stack’s monitoring/controller requirements.

Discovery now exposes exactly one RMS output: a link to a self-contained Redwood-styled HTML report in Object Storage. It contains model/checkpoint metadata, context/concurrency memory estimates and their limitations, every confirmed capacity option in a collapsed section, recipe commands/configuration, both child-stack link groups, and regional capacity/limit evidence. Zero-option assessments still produce a page. Opening/filtering the page performs no additional discovery calls.

Recommendations now prefer hardware fit and confirmed growth rather than minimum allocated GPUs: VRAM per GPU, GPU/host sharding, RDMA capability, additional whole replicas covered by AD capacity and entitlement, then regional physical supply/allocation tie-breakers. The report places deployment actions before serving configuration and hides zero/unknown-only supply rows while retaining positive-capacity limit-review options. Known unquantized weights and Qwen full-attention KV payload stay visible independently of the unprofiled complete hybrid/vision allocation; the planning-budget formula is explicit. See [the recommendation and memory work](discovery-recommendations-plan.md).

Both configured infrastructure and model ZIPs are generated during discovery. The infrastructure stack owns retained GPU allocation and shared controllers. Each model stack creates an independent DevOps project/environment/repositories and four deploy/validate/benchmark/undeploy pipelines. The normal model form asks only for the cluster: native lookups resolve network and compatible managed GPU-pool metadata, with advanced overrides for ambiguity. Missing GPU allocation/controller readiness does not prevent metadata creation; runtime execution checks the real platform later. No completed infrastructure binding JSON is required.

Live RMS discovery publication, PAR downloads, hosted report rendering and native validation of generated ZIPs passed. The cluster-only model stack passed live RMS Plan/Apply without a GPU pool. Service API checks confirmed its independent project/environment, four ACTIVE model pipelines and six ACTIVE stages (one native Helm, five Shell). No pipeline was executed. See [the validation record](discovery-html-validation-2026-11-14.md).

The shared CPU component foundation was previously validated live: LWS reuse, parallel Prometheus/KEDA installation, fresh aggregate readiness and guarded KEDA uninstall/reinstall retaining six KEDA CRDs. See [that validation](native-component-validation-2026-11-13.md). Prometheus and the shared KEDA controller default on; model autoscaling remains opt-in and LWS follows topology. Existing CPU pools host controllers; infrastructure creates no CPU pool. The temporary `skip_gpu_allocation` debug flag suppresses allocation only and must never be enabled after retaining GPU hosts.

Model workloads use a repository-owned native Helm chart for Deployment/LWS and an optional pinned Production Stack router dependency. Native Helm and artifact-backed Shell stages remain explicit operations. Shared components have platform lifecycle; model releases, routes/cache instances and scaling resources have model lifecycle. Small scripts/configuration use readable inline artifacts; required larger file inputs and downloadable benchmark results use Generic Artifacts, routine status/failure/readiness summaries use DevOps Logging, and charts use OCIR; Object Storage holds discovery bundles/reports and explicitly selected retained model data.

## Remaining work and validation limits

- Update existing platform onboarding delivery to the current independent-project identity flow before onboarding new model projects. Cross-project authorization has local executable coverage; it was not run against Kubernetes in this validation. Model runners receive namespace writes and bounded shared read access, not cluster administration. Generic Artifact IAM is still compartment-scoped.
- Execute GPU allocation and actual model deploy/validate/benchmark/undeploy only when authorized. Driver/CUDA/NCCL/RDMA, scheduling, inference modalities, cache behavior and performance remain unvalidated on hardware. Free headroom across other model namespaces is unknown until scheduling/rollout succeeds.
- Native OKE add-on enablement is implemented in infrastructure Apply: NFD, existing-or-new NVIDIA GPU integration, RDMA Network Operator when required, and a compatible bare-metal GPU Health Monitoring controller. Existing settings and shared services are retained. Installation has offline coverage; live enablement, per-pool health configuration, RDMA device configuration and GPU telemetry scraping still need validation/work. See [the module lifecycle](../modules/cluster-add-ons/oke-managed-addons/README.md).

- Implement additional explicitly supported cache/P-D/Ray/gateway adapters and durable shared Responses conversation history as required. Recipe flags alone do not install these services. A vLLM operator is optional rather than a universal prerequisite.
